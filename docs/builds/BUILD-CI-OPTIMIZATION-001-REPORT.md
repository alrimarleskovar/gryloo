## 3. Root-cause analysis

The serial runner makes duplicated jobs and queue delays expensive. Initial
GitHub evidence showed push and PR executions for the same branch updates.
Registry review fetched large uncompressed full npm documents for each version.
There are 265 locked versions but only 259 names. Tool archives were downloaded
and extracted afresh every job. Browser validation dominates and intentionally
starts a fresh fixture/server boundary for every guarded profile.

Updated-main logs identify `lending-composition-service.test.ts` as the slowest
unit file: 61 tests in 135.961s, within a 151.57s Vitest unit run. PostgreSQL's
WhatsApp journey file takes 16.310s; repay/router/supply unit files take
16.710s/15.343s/13.937s. Browser cases include swap-read acceptance at 14.0s,
BUILD-009 restoration at 12.1s, the EVM in-chat journey at 10.6s, and the ChatGPT
channel-signing fixture at 8.9s. These are logged file/case durations, not
isolated CPU measurements or additive job costs. Financial expectations,
fixture isolation and timeouts are unchanged.

Repeated full Next compilation was **not** found: production builds once, and
Playwright uses `next start`. Turbo already reuses seven dependency builds
between typecheck and build in the same fresh job. Frozen installation already
uses the runner's existing store efficiently. No evidence supports increasing
Turbo/Next/test/browser parallelism on this shared 8 GiB host.

## 4. Implemented optimizations

- Full npm metadata requests negotiate gzip and fetch once per name. All pinned
  versions, publication times, integrity/license/platform/route checks, current
  release-age evaluation and existing exact exceptions remain mandatory. No
  metadata or approval evidence is cached between jobs. Eight network workers
  are retained; duplicate JSON parsing and responses are reduced.
- Four public raw approved archives use immutable official
  `actions/cache@caa296126883cff596d87d8935842f9db880ef25` (v5, Node 24).
  Cache hits only avoid downloads; verification and fresh extraction still run.
- Workflow-specific PR concurrency supersedes older executions of the same PR.
  Every push uses its run ID, protecting all active/pending main certifications.
- Individual native steps expose typecheck, lint, production build, schemas,
  units, Anvil/browser bootstrap and suites. Dependency audit runs before costly
  validation; the unchanged SBOM gate stays at the end.
- Standard-library Python/Bash records duration, outcome, system CPU/I/O/swap
  counters and endpoint RAM. Success/failure summaries identify the slowest
  completed stage. Guarded profiles log individual duration and PASS/FAIL.
  Existing owned composition cleanup runs through the observer's EXIT hook.

Both push/PR triggers remain: governance explicitly requires both and forbids
conditional required gates. Dynamic push/PR deduplication would need a broader
certification design. No skipped successful placeholder checks were introduced.

## 6. Cache security assessment

**Locally verified; two remote cold/save observations verified; warm restore pending.** Contents are exactly the
Node 24.21.0 x64 tar.xz, pnpm 11.22.0 tgz, Foundry 1.8.3 tar.gz and approved
headless-shell revision 1243 zip. No extracted executable, build/test result,
node_modules, database, journal, key, signed manifest or session is exported.

The key includes an explicit schema epoch, OS/architecture, exact tool versions,
bootstrap/cache verifier hashes, lockfile, npmrc and pnpm workspace config. No
restore-key prefixes or cross-OS reuse. A configuration/source/pin change
invalidates the bundle. An exact Actions cache hit is not approval of its bytes.
GitHub's [cache access rules](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
separate PR merge-ref caches from protected-branch caches; independently, every
consumed raw archive is cryptographically checked against reviewed source pins.

Read-only cache API inspection confirms the push entry `8731870286` is scoped
to `refs/heads/codex/build-ci-optimization-001`; the PR entry `8734365070` is
scoped to `refs/pull/74/merge`. Both have key
`flofi-archives-v1-Linux-X64-node24.21.0-pnpm11.22.0-anvil1.8.3-browser1243-ccf952a87a95f18a17ebf65597817a15acfac59dfd4f35361a051c5b9d8b5095`
and cache version
`9297aa8ae7198baa091bf47252bd6638629aae6fc6c887562d911341d7971839`.
The push entry was created at 13:42:30 UTC, before the PR restore attempt at
14:18:42 UTC, yet the PR did not reuse it. The PR entry was created at
14:40:38 UTC, after its successful save. Equal keys alone therefore did not
provide cross-ref reuse in these observed runs; this was not key invalidation.

GitHub documents branch/default/base cache access restrictions and that a
`pull_request` save belongs to its merge ref, available to reruns of that PR
and unavailable to its base branch or other PRs. This is ref scope, rather than
an event-name component of this implementation's key. An unchanged rerun of
run `37939446349` should be eligible for the saved PR entry while it remains
available, but eligibility is **not an observed HIT**. No ref/permission
override or cache deletion was performed to manufacture reuse.

Cached files must be regular, non-symlink files; FIFO reads cannot hang the job.
Size checks reject oversized entries. A private disk copy is hashed before
archive parsing. Corruption/misses trigger the existing restricted downloader
and then hashing; unavailable or invalid downloads fail. Node's official
checksum listing is still fetched on every bootstrap. Browser/Anvil source and
redirect restrictions, entry validation and binary/version checks are retained.
Fresh extraction prevents trusting modified extracted files. No security gate
is conditional on cache status. Caches save only after a successful job.

Cold starts download/verify all four archives; warm starts restore, rehash and
re-extract. Immutable bad cache entries may cause repeated verified downloads;
bump the cache epoch or revert the cache action if transfer/storage costs are
unhelpful. Removing cache configuration restores mandatory verified-download
behavior. No shared runner/global cleanup is needed.

The observed 105s push save and 204s PR save are material: the latter alone
exceeds the PR's 35.242s combined archive-acquisition intervals. These cold
costs do not measure warm restoration or establish net benefit over repeated
runs. Retention/removal remains pending until a real HIT measures transfer,
restoration, re-verification and fresh extraction, with save/cleanup costs
included in full wall time. Separate phase timers are absent from the existing
revision, so exact hashing/extraction values must not be inferred from total
bootstrap time. Local setup hits do not establish remote transfer benefit.

Rejected: new pnpm cache (2s install; negligible measured opportunity), Turbo
outputs/cached typechecks, Next build cache and TypeScript incremental files
(unverified executable/state reuse across trust boundaries). Existing ephemeral
within-job Turbo reuse remains intact.
